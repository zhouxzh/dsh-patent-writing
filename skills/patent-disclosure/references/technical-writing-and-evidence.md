# 技术写作、论证与证据

## 从事实到技术模型

先把材料分为：

- **已实现**：代码、原理图、样机或记录直接证明相应功能；代码存在不等于完成板端测试。
- **已确定设计**：发明人确认了结构、参数或控制关系，但可能没有样机。
- **助手建议**：为补全交底而提出、尚未获得发明人确认的设计。
- **待验证效果**：理论推导、设计预期或验证计划。
- **公开状态**：私有、送样、展示、论文、销售或用户披露。

对每个关键部件说明输入、输出、执行主体、前置条件、失败状态和与相邻部件的关系。发现矛盾先记录具体冲突，不擅自补造电路或算法。

## 学术论文/技术报告写法

推荐单章逻辑：

> 研究问题 → 已知方法及限制 → 技术目标 → 方案结构 → 原理与公式 → 实现步骤 → 参数选择 → 实验设计 → 边界与替代方案。

写作要求：

- 术语首次出现时定义，英文缩写给出中文名和全称。
- 公式前交代假设，公式后逐个解释变量、单位和适用范围。
- 算法写清输入、输出、窗口、阈值、更新规则、状态迁移和终止条件。
- 参数不仅要给数值，还要说明来源：器件限制、设计要求、标定、仿真或下文待冻结。
- 用具体因果句代替形容词，例如说明“该状态为什么能阻止旧结果进入当前测量”。
- 较复杂段落先给一句结论，再解释机制和条件；不要把结论埋在长句中。
- 不同事实等级直接标明，不靠模糊语气混在一起。

## 技术问题与发明目的

问题应包含物理、数据或控制原因。例如，不应只写“现有设备精度低”，而应说明：

- 哪一级先饱和；
- 哪个状态未绑定；
- 哪类旧消息可能进入新配置；
- 哪个参数没有可观测依据。

目标应与后文手段一一对应。不要用“更智能”“更稳定”作为无法验证的目标。

## 创新点分析

每项候选创新至少写成：

| 项目 | 内容 |
| --- | --- |
| 现有做法 | 已知结构或步骤 |
| 本方案改变 | 新增、替换或重组的连接或动作 |
| 作用机制 | 为什么改变输入、误差、状态或控制 |
| 实施条件 | 必需硬件、参数和前置检查 |
| 证据 | 公式、器件约束、仿真、台架或实测 |
| 检索边界 | 已核实相同点、明确差异、待检索组合 |
| 实现状态 | 已实现、已确定设计或建议 |

多个创新点可以同稿说明，但应写清它们共享的输入、状态或控制关系。不要仅按功能数量判断创新，也不要为显得创新而删掉实现细节。

## 效果与对照

效果说明回答三层：

1. 对比方案在什么条件下失败；
2. 本方案通过哪个具体结构或动作改变该条件；
3. 产生何种可观察差异，边界在哪里。

可以使用设计计算、器件手册、仿真、台架或整机测试。没有测试时写明“设计预期”或“拟验证”，不能编造百分比、置信区间或样机结果。

## 验证设计

必要时设计以下对照：

- 现有方案基线；
- 关键机制的单项作用；
- 完整组合；
- 失效反例和适用范围外样本；
- 与问题直接相关的指标。

记录设备、材料或探头、版本、原理图、固件、原始数据、脚本和环境。计划中的样本量、阈值和判据只是设计选择。若使用统计判定，说明采样单位、分组和不确定度，但不强制所有项目采用同一统计框架。

## 去模板化

删除没有技术信息的引导和总结。营销词改为机制描述；重复的免责声明集中到事实说明；相同段首和排比结构应改写。必要限制不得删除，例如上电调零条件、源变化未决、异常锁存和模拟上游饱和边界。

不要用“AI 检测率”评价文本，也不声称某种词频能证明作者身份。
